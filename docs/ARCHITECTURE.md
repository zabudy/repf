# Архитектура REPF

Входом служит исторический ряд или характеристики квартиры с историей продаж. Асинхронный REST API создаёт задачу в SQL. Воркер подготавливает данные, запускает цикл агентов и сохраняет прогноз вместе с трассировкой.

## Цикл прогноза

| Компонент | Ответственность |
|---|---|
| [DataAnalyst](../backend/agents/data_analyst.py) | Приводит ряд к календарной сетке, извлекает признаки. Для квартиры сводит историю цен и метаданные рынка. |
| [ModelSelector](../backend/agents/model_selector.py) | Ищет похожие кейсы в базе и выбирает зарегистрированный инструмент. Допустимые гиперпараметры описаны JSON Schema. |
| [Forecaster](../backend/agents/forecaster.py) | Считает прогноз, ошибки на временных отложенных окнах и калибрует интервал. |
| [Validator](../backend/agents/validator.py) | Проверяет длину и допустимость прогноза, остатки и качество на отложенных данных. |
| [Critic](../backend/agents/critic.py) | Даёт оценку и пояснение по метрикам и диагностике. При сбое провайдера применяется локальная формула. |
| [Supervisor](../backend/agents/supervisor.py) | Координирует до трёх итераций. При необходимости меняет инструмент и переводит задачу на проверку. |

[ForecastState](../backend/core/forecast.py) содержит Pydantic-поля, ссылки на вход, предобработанный набор и результат. Объекты NumPy и pandas живут в хранилище артефактов конкретного запуска. В SQL сохраняются исходный запрос, небольшие структурированные поля состояния и итог. При повторе задачи вход восстанавливается из SQL.

У режимов общий механизм проверки. В базовом режиме (`baseline`) для ряда используется сезонный наивный прогноз и последнее наблюдение при нехватке сезона, для квартир — Ridge. «Подбор по аналогам» (`+rag`) выбирает модель по взвешенному голосованию похожих кейсов без вызова LLM. «Агенты + RAG» (`+agents`) передаёт найденные кейсы в LLM и добавляет Tool Calling, до трёх итераций, Critic и HITL.

## Инструменты

| Тип | Модели |
|---|---|
| Временной ряд | Holt с затухающим трендом, авторегрессия с опциональной первой разностью, регрессия с гармониками Фурье |
| Квартиры | Гедоническая Ridge-регрессия, взвешенные ближайшие соседи, градиентный бустинг над одноуровневыми деревьями и взвешенный ансамбль этих трёх моделей |

Реестр валидирует имя, тип задачи, поля аргументов и их границы. DeepSeek получает списки функций и агрегированные признаки с кейсами. Нативные вызовы и ответы в JSON проходят одинаковую локальную проверку. Последовательно пробуются доступные провайдеры, затем JSON-ответ первого провайдера. Если допустимого вызова нет, выбор опирается на похожие кейсы и локальные правила. [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

Для квартиры регрессия оценивает отношение цены к месячному уровню рынка. Оно применяется к траектории месячного индекса. Из оценки выделяются цена за м² и пять крупнейших вкладов поля через точное перечисление коалиций Шепли относительно одного опорного объекта.

## Поиск похожих кейсов

1. Статистические и спектральные признаки стандартизуются по корпусу и преобразуются PCA в вектор размерности 128.
2. Описание кейса дополняется контекстом о частоте, тренде, сезонности и корреляции. Для квартир в контекст входят тип задачи, район, цель и число признаков.
3. BM25 и косинусное сходство возвращают отдельные рейтинги. В локальном режиме плотный поиск работает через NumPy, в Compose через Qdrant с версией корпуса.
4. RRF объединяет рейтинги. Поиск ограничен совместимым типом задачи и частотой или типом табличной цели.

## Задачи, трассировка и проверка

`pending → running → completed | waiting_for_human | failed`. При ручном повторе задача возвращается в `pending`. Статус и версия попытки обновляются условным запросом, чтобы два воркера не завершили одну попытку одновременно. У задач есть срок аренды на случай остановки воркера.

Фоновый обработчик в локальном режиме читает SQL-очередь. В Docker Celery beat передаёт воркерам задачи обработки очереди через Redis. UI опрашивает статус и дерево шагов приблизительно раз в 700 мс.

`reasoning_logs` хранит дерево действий с `parent_id`. `llm_calls` хранит модель, результаты проверки вызова, токены, время и хэши. Сохраняются наблюдаемые действия и диагностика. LLM-кэш хранит только поля структурированного ответа и живёт 12 часов. Прогнозы базового режима кэшируются для того же пользователя и запроса. Ручное решение записывается в историю и отдельный шаг трассировки. Принятый прогноз создаёт запись экспертного кейса в SQL. Такие оценки служат материалом для последующей проверки и попадают в общий поисковый индекс только после подготовки проверяемых наблюдений.

Исторические модели `Property`, `Forecast` и `ExpertFeedback` из первых этапов сохранены. Основной REST-процесс работает через `ForecastTask`, `EvaluationRun`, `ReasoningLog`, `LLMCall`, `KnowledgeCase`, `GlossaryTerm`, `CacheEntry` и `User`. Таблицы создаются при инициализации.

## Выбор LLM аккаунта

`llm_checkpoints` хранит проверенные пресеты пользователя. `llm_selections` содержит указатель на активный пресет. При создании и переключении облачная или локальная LLM должна вернуть допустимый вызов инструмента на пробных данных. Ошибка оставляет текущий выбор прежним. Воркер читает активный пресет владельца задачи перед началом расчёта. Ключи шифруются. Существующие профили из `llm_profiles` доступны в списке как «Ранее сохранённая модель». Эксперименты по умолчанию используют детерминированный mock и работают независимо от выбранного пресета.

Чат по прогнозу использует активный пресет владельца на момент отправки вопроса. Модель получает сводку результата и до шести предыдущих пар сообщений. Переписка хранится на открытом экране до перезагрузки, перехода к другому расчёту или выхода из аккаунта. В журнал приложения пишутся модель, статус, время и токены вызова. [Формат запроса](API.md)
